# 进程退出挂死调查记录

> **状态：已归档。** 结论已收敛为「长时会话累积的 OS/驱动级环境现象，与本项目代码无关」。
> **现状见**：[窗口 §5-C2 / §6](../window.md)（约束与自检判定）、
> [自检判定 §4](../window_automation.md)（不看退出码）、
> [宿主边界 §4](../window_host.md)。
> 本文保留复现矩阵与修正过程，仅供溯源。

调查时间：2026-09-22 起，2026-09-23 深夜修正，2026-09-23 01:10 重启后复测。

---

## 1. 最初的结论（09-22，后被推翻）

最小复现矩阵（本机，DPG 2.3.1）曾指向「只要渲染过帧就挂死」：

| 用例 | 结果（09-22） |
|------|------|
| 不 import dpg | 正常退出 |
| `create_context` + `destroy_context`（不建视口） | 正常退出 |
| 建视口 + `show_viewport`，**一帧都不渲染** | 正常退出 |
| 渲染 30 帧 → `stop_dearpygui` → `destroy_context` → `sys.exit` | **挂死** |
| 同上但改用 `os._exit(0)` | **一样挂死** |

## 2. 修正（09-23 深夜）：与 DPG 无关

把 DPG 完全移出变量后重跑对照：

| 用例 | 结果（09-23 01:00 前后） |
|------|------|
| 纯 Python（`python -c "print('hi')"`） | 0.2s 正常退出 |
| **纯 Tk**：建根窗口 → `update()` 循环 1.5s → `destroy()` → `sys.exit(0)`（**全程不 import dpg**） | **挂死** |
| Tk + DPG 手动渲染 → `destroy_context()` → 全部收尾语句执行成功 | **挂死**（收尾语句都执行完了，卡在解释器退出） |
| Tk + DPG 用**旧** `start_dearpygui()` 驱动 | **崩溃**（0xC0000005，见 §5） |

也就是说：**在这个环境里（深夜这个时段），任何建过 GUI 窗口的 Python 进程都可能退不出去**，
与 DPG、与驱动方式都无关；卡点在 Python 之下（`os._exit` 绕不过），卡住后 `Stop-Process -Force` 也杀不掉。
实测 `threading.enumerate()` 无残留非 daemon 线程，所以不是「有线程没退出」这类 Python 层原因。

它还是**间歇性**的：09-22 17:00 前后同样的脚本连续 4 次都干净退出（退出码 0），00:30 之后同样形状全部挂死。

## 3. 重启后复测（09-23 01:10 后）：不再复现

机器在 01:09:59 重启，重启后立刻用同一批最小脚本复测（脚本留在
`%TEMP%\dungeon_spike\hang_check.py` / `hang_repeat.py`）：

| 用例 | 结果（重启后） |
|------|------|
| `py`：纯解释器 | rc=0，0.2s（×2） |
| `tk`：建根窗口 → `update()` → `destroy()` | rc=0，0.6s（×2） |
| `dpg`：建视口 → 手动渲染 30 帧 → `stop` → `destroy_context` | rc=0，**0.8s**（×2） |
| `inproc10`：**同一进程**内 create/render/destroy 10 轮（100 帧） | 10 轮全过，父进程 rc=0 |
| `loop8`：**8 个独立子进程**各跑一轮 | 8 轮 rc=0，各 0.8~1.0s |
| 自检 4 个场景子进程 | 全部**自行退出 rc=0** |

三条结论：

1. **重启即消失**，且重启后 18 次 GUI 生命周期（含 10 轮同进程累积）无一挂死 → 是**长时会话累积出来的
   OS/驱动级状态问题**（当晚已连续跑数小时、反复创建销毁 DPG 视口，还留过杀不掉的孤儿进程），不是本项目代码的 bug。
2. **不是累积在进程内的**：同一进程 10 轮 create/destroy 干净退出，说明「多开几次副本就会卡」这个担心不成立。
3. 对架构选择的影响因此收敛：**不必为了「防挂死」提前做 L5 进程隔离**；自检继续按「读输出判定 + 父进程
   超时兜底」（成本为零），但**不要**把退出码当失败信号；真遇到症状时**先重启系统**再复现。

副产品：自检原先的「立刻 poll → 判定挂死」会误报——正常子进程在结论行后约 0.1s 就退出了，
这才加了 `EXIT_GRACE`（5s）宽限。

## 4. 对自检的长期影响

- 判定成败**看子进程打印的结论行，不看退出码**。
- 每个场景开**子进程**（单场景用 `--isolate`），父进程读到结论行后等 `EXIT_GRACE` 宽限，仍不退出才 `kill()`。
- **Python 层的看门狗无效**：DPG 循环期间 `threading.Timer` 可能拿不到 GIL，实测 40s 定时器根本没触发。
  超时只能由外层（父进程）兜底；真正卡住时 `os._exit` 与 `Stop-Process -Force` 都无效。

## 5. 另一条实测（真崩溃，与挂死不同）

`destroy_context()` **之后**再调用任何 Tk API（`root.update()` / `root.destroy()` / `winfo_*`）
会以 0xC0000005 直接死掉，且**新旧两种驱动都能复现**（老驱动崩在 `destroy_context` 之后第一次 Tk 调用）。

实测（2026-09-23，DPG 2.3.1 + Py3.13）：Tk 根窗口 + DPG 视口，销毁 DPG 上下文后再碰 Tk 即崩；
用旧的 `start_dearpygui()` 驱动**同样复现**，所以这不是手动渲染引入的问题，而是 DPG 原生收尾与 Tk 的相互作用。
对照：全程不 import DPG 的纯 Tk 用例不会崩。

真应用不受影响，因为它的 Tk 交互（宿主显隐、`_handle_exit` 的弹框）全部排在 `destroy_context()` 之前——
`base._finish_session()` 的顺序就是为此固定的。自检脚本里「会话结束后销毁 Tk 根窗口」这种收尾也要避免
（`scene_tk_host` 故意不销毁根窗口，留在 `_KEEP_ALIVE_ROOTS`）。
