# 副本关系图与图校验

> **定位**：章节与触发器之间到底存在哪些关系、这套方案能不能从起始章节走通、编辑器里
> 怎么一眼看清。字段定义见 [数据模型](script.md)，校验器的其它规则见 [数据模型 §9](script.md)。
> 图的**分析**在 `dungeon/scenario_graph.py` / `dungeon/graph_lint.py`（领域层、纯数据），
> **呈现**在 `ui/scenario/graph_view.py`（编辑器）。

## 1. 为什么不止「前置条件」一条关系

分章节之前，触发器是平铺的，互相之间只有 `precondition_names` 一种关系，所以早期的
「检查动态」只画这一种边就够了。分章节之后，决定一次副本能不能走通的实际上有**四条**
互相独立的路径，任何一条断了都不会报错，只会静默不生效：

| 关系 | 从配置哪里读出来 | 断了会怎样 |
|---|---|---|
| 前置条件 | 触发器的 `precondition_names` | 条件永远不成立，触发器永不触发 |
| 章节跳转 | `goto` 动作的 `action_data.chapter` | 目标章节永远进不去 |
| 超限跳转 | 章节的 `overflow_target` | 段落数到上限后无处可去 |
| 条件引用 | 条件键 `选择:<触发器名>` | 计数永远为空，分支永远走不到 |

再加上**归属**关系（触发器靠 `chapter` 字段声明自己属于哪一章），这套结构才完整。
四条路径 + 归属，就是下面这张图模型。

## 2. 图模型（`dungeon/scenario_graph.py`）

`build_graph(config)` 是唯一入口，返回 `ScenarioGraph`。**零外部依赖**——不再需要
`networkx`（强连通分量与可达性都是自实现的）。

### 2.1 节点

| 种类 | id 约定 | 携带的信息 |
|---|---|---|
| `NODE_ROOT` | `root` | 「（无章节）」起点伪节点，代表副本刚开始、还没进入任何章节的状态 |
| `NODE_CHAPTER` | `chapter:<章节名>` | 起始 / 结束 / 固定文本标记、在 `chapters` 里的下标 |
| `NODE_TRIGGER` | `trigger:<触发器名>` | 归一化后的动作类型、所属章节、在 `triggers` 里的下标 |

触发器名与章节名已经是校验器认定的唯一键，所以直接拿名字当 id，不另造一套。

**入口为什么是伪节点而不是起始章节**：运行时 `_enter_start_chapter` 是在
「当前没有章节」时才进入起始章节的。从伪节点出发算可达性，才能同时覆盖
「没有标记起始章节」和「某章节永远进不去」两种情形。

### 2.2 边

| 种类常量 | 展示名 | 方向 | 来源 |
|---|---|---|---|
| `EDGE_ENTRY` | 进入 | `root` → 起始章节 | `chapters[].start` |
| `EDGE_SCOPE` | 归属 | 章节 → 其下的触发器 | `triggers[].chapter` |
| `EDGE_PRECOND` | 前置条件 | 前置触发器 → 触发器 | `triggers[].precondition_names` |
| `EDGE_GOTO` | 章节跳转 | 触发器 → 目标章节 | `goto` 动作的 `action_data.chapter` |
| `EDGE_OVERFLOW` | 超限跳转 | 章节 → 目标章节 | `chapters[].overflow_target` |
| `EDGE_CHOICE` | 条件引用 | 被引用触发器 → 触发器 | 条件键 `选择:<触发器名>` |

`EDGE_SCOPE` 只参与分析，界面上不画箭头——它由泳道归属直接表达（§4.2）。
范围是「任意章节 / 无章节」（`CHAPTER_ANY` / `CHAPTER_NONE`）的触发器，归属边从
`root` 出发：它们在任何状态下都可能判定。

### 2.3 两个可达性口径（关键约定）

图校验要报 error，就必须**宁可漏报不可误报**。因此有两条口径，别混用：

- **章节可达性**（`chapter_reachability()`）：只走 `entry` / `goto` / `overflow` /
  `scope`，**忽略一切条件与前置**。这是乐观估计——结构上到得了就算到得了，
  不会因为条件写错而误报。error 级的规则只用这一条。
- **触发器可达性**（`trigger_reachability()`）：在上面基础上加入 `precond` 的
  AND 语义。先把前置边收缩成强连通分量，再在 DAG 上迭代到不动点；一个分量要能激活，
  必须**存在一个成员没有分量内的前置**（"种子"）。整环互锁、没有种子的分量永远激活
  不了——这正是「循环依赖」的判据。

`EDGE_CHOICE` 两条口径都**不参与**：被引用的触发器没触发只意味着计数为 0，
是可以被比较的合法值，不是"到不了"。

### 2.4 泳道与章节层投影

- `lanes` 按编辑器的顺序给出泳道：每个章节一条，顺序同 `chapters`；「任意章节 / 无章节」
  的触发器合成最后一条。每条泳道里是节点 id 序列。
- `chapter_view_edges()` 把图投影到**章节层**：`goto` 边折算成「触发器所在章节 → 目标
  章节」，用于「章节总览」视图（章与章之间的流程图）。
- `same_position_groups()` 把 `ACTION_POSITIONS` 同位、同作用域、且**不止一条**的触发器
  分好组（`PositionGroup`），供编辑器呈现同位置竞争（§3.2）。它只分组，不下结论。

## 3. 图校验（`dungeon/graph_lint.py`）

```python
lint_graph(graph) -> list[tuple[str, str, str]]   # (level, path, message)
```

这个模块**不 import `validate`**：它只产出三元组，由 `validate.py` 侧包成
`Diagnostic`。这样避免 `validate → graph_lint → validate.Diagnostic` 的循环 import，
也不用在函数体里写延迟 import。

### 3.1 五条规则

| # | 规则 | 级别 | `path` | 判据 |
|---|---|---|---|---|
| R1 | 章节走不到 | `error` | `chapters[i].name` | 章节可达性 |
| R2 | 走不到任何结束章节 | `warning` | `chapters` | 结束章节存在，但一个都不可达 |
| R3 | 前置永远无法成立 | `warning` | `triggers[i].precondition_names` | 前置所在章节不可达，或前置自身处于死锁分量 |
| R4 | 自跳转 | `warning` | `triggers[i].action_data.chapter` | `goto` 目标 == 自身所在章节 |
| R5 | 循环依赖 | `warning` | `triggers[i].precondition_names` | 前置分量无种子成员 |

### 3.2 三条口径要说清

**可达性规则只在方案真的会在章节间移动时才生效。** R1 / R2 都要求「至少有
一个起始章节」且「至少有一条跳进章节的边」（`goto`，或指向章节的 `overflow_target`；
空 `overflow_target` 是「超限后离开章节」，不算接线）。理由：一节都没接线的方案
——多半就是从 `empty_scenario_config()` 改出来的骨架——除起始章节外全部不可达，
逐章刷一遍只是噪音；没有起始章节时顶层已有一条 error，重复报更没有意义。

**没有可达的结束章节时，结束章节不再逐条报 R1。** 那种情况下 R2 的措辞更准确
（「这一局收不了尾」）；两条都报等于同一个原因刷两遍。反过来，只要**有一个**结束章节
可达，其余走不到的结束章节照旧按 R1 报——那是实实在在「这段内容播不到」。

**同位置动作竞争不进校验器。** 运行时 `ACTION_POSITIONS` 同位置至多生效一个
（同位置内按配置顺序取第一个满足条件且配置有效的），所以同位置同作用域的两条触发器
确实会互相挡。但严格判断「两条的条件会不会撞车」需要求解器、不可行；连「两边都恒真」
这一种也不报——`{"name": "ok", ...}` 与 `{"name": "clear", ...}` 这种一设一清的写法
在参考方案与门禁用例里都出现过，报红等于把正常写法当缺陷（本仓一贯的降噪口径）。
`same_position_groups()` 因此只把成员分好组，由关系图对话框按位呈现（§4.3）：
作者点一下就能看见谁和谁在争同一个位次，无争议的那几条还会写明「永远轮不到」。

**R2 与现有的 info 不重复。** `validate.py` 原有的规则是「方案里根本没有结束章节」，
报 `info`；R2 说的是「结束章节存在、但一个都走不到」，两者不是一回事。

### 3.3 接入点

管线不新增：`validate_scenario_config()` 在 `_validate_triggers` 之后调用
`lint_graph(build_graph(config))`，把三元组 `add` 进同一个诊断列表。因此保存方案、
启动副本前、离线批量校验三处**自动**都覆盖到了，`format_diagnostics` / `has_errors`
直接复用——`error` 级照旧阻止进入副本。

## 4. 编辑器关系图（`ui/scenario/graph_view.py`）

`ScenarioGraphDialog` 由「检查动态」按钮打开（`chapter_trigger_mgr.check_dependencies`）。
它是**只读**的：不做编辑、不写盘，双击节点不会打开编辑框。

### 4.1 布局

```
┌ 分段切换：章节总览 / 触发器依赖 / 清单 ────────────────┐
│ 图层开关 │            画布 / 清单            │ 校验诊断 │
│ 四类边   │  （tkinter.Canvas 自绘，可平移缩放）│ 点击定位 │
│ 只看问题 │                                   │          │
├ 汇总：N 错误 · N 警告 · N 提示 ───── 导出报告 · 关闭 ┤
└──────────────────────────────────────────────────┘
```

### 4.2 三个视图

| 视图 | 内容 | 用什么画 |
|---|---|---|
| 章节总览 | 章与章之间的流程图，按可达深度分列 | Canvas，节点是章节 |
| 触发器依赖 | 泳道式：一条泳道一个章节，泳道内按依赖分层（列 = 依赖深度，行 = 同层逐个） | Canvas，节点是触发器 + 章节抬头 |
| 清单 | 章节 → 触发器的树形大纲，带问题徽标 | `ttk.Treeview` |

「触发器依赖」用泳道而不是通用分层布局：图只有几十个节点，而泳道恰好就是
「分层查看章节关系」最直接的表达——归属不用画箭头，排在本章节的泳道里即可。
泳道**内**再按依赖分层：章节抬头在第 0 列，泳道内没有前置 / 条件引用来源的触发器
在第 1 列，其下游依次向后；同列内每个节点各占一行，下游从来源所在行起步。
这样「一个枢纽触发器被多条触发器引用」时，那些下游各占一行、缩进在枢纽右侧，
前置 / 条件引用连线向右扇出。若把同一章节的触发器一律横排成一行，这些下游就会
挤在一起、连线也叠成一条横线，看起来像链式依赖（很容易读错）。

同理，泳道视图里章节跳转（`goto`）与超限跳转（`overflow_target`）都不画指向
目标章节的跨泳道箭头——那会把视线频繁拽出泳道——只在节点右上角画一个 ↗ 跳出
角标（触发器上是章节跳转：蓝实线；章节抬头上是超限跳转：橙虚线），目标从
详情面板看。跨章节箭头只保留触发器→触发器这种（前置条件引用了另一章的触发器）；
「章节总览」视图仍照常画章节层的跳转箭头。

### 4.3 交互

- 拖拽平移、滚轮缩放（画布自己的坐标变换，不重建控件）。
- 点节点：高亮它的入边与出边，取消其它高亮；左侧详情把**直接依赖它的其他触发器**
  （前置 / 条件引用）与**同位置竞争的组员**（`same_position_groups()`）都
  一触器一行列出来，`▸` 标出选中的那个——被多处引用的枢纽触发器（选项、小游戏、
  条件标记）不会挤成一长行。同位竞争里「恒真且配置顺序靠后、永远轮不到」的成员
  单独列出。这是校验器不报、但作者最需要看见的一类信息。
- 点右侧诊断：切到能显示该节点的视图、滚动到它并选中。
- 图层开关关掉某类边即不再绘制（诊断列表不受影响，仍报全部问题）。
- 「只看有问题的」：只留下带诊断的节点与它们之间的边（同位置竞争不是诊断，
  因此不受这个开关影响）。
- 「导出报告」除了诊断，还单列一节「同位置竞争」，方便脱离界面核对。

### 4.4 配色

图相关 token 在 `assets/theme/{Slate,Classic}.json` 的 `vars` 里，**两套配色必须
成套一致**（结构不一致换配色会炸）：

| 前缀 | 用途 |
|---|---|
| `GRAPH_EDGE_*` | 按边种类分色（前置 / 跳转 / 超限 / 引用 / 进入）+ `GRAPH_EDGE_ERR` |
| `GRAPH_NODE_*` | 节点边框、问题节点的填充与边框 |
| `GRAPH_LANE_*` / `GRAPH_CANVAS_*` | 泳道底色 / 画布底色 |
| `ACTION_FILL_*` | 触发器节点按动作类型着色（沿用旧依赖图的映射） |
| `DEPENDENCY_*` | 汇总与诊断文字（沿用） |

章节节点用章节自己的 `color`，深色模式下经 `chapters.shade_for_mode` 提亮 35%，
与章节/触发器面板的行着色同一套规则。

## 5. 自检

| 脚本 | 覆盖 | 命令 |
|---|---|---|
| `tests/check_scenario_graph.py` | 离线（可进 CI 门禁）：节点与四类边构造、两个可达性口径、强连通分量与种子判定、五条规则各命中一次、骨架方案不刷可达性诊断、同位置竞争只分组不报红、正常方案零诊断、`path` 与既有诊断体系一致 | `python tests/check_scenario_graph.py` |

GUI 侧没有独立的守卫脚本：画布只做呈现，逻辑全在领域层的两个模块里，那部分已被上面
的离线自检覆盖。手工看效果用
`python tests/run_checks.py --smoke`（进编辑器点「检查动态」）。

## 6. 边界（明确不做什么）

- **不写盘**：全程只读方案配置，产出的是诊断与图形。
- **不做条件求解**：只见「条件是否为空」，不判断两个非空条件是否重叠（见 §3.2）。
- **不替代既有规则**：图校验是**追加**的五条，`validate.py` 原有的字段级、资产存在性、
  旧版字段等规则一条不动。
- **不再依赖 `networkx` / `graphviz`**：两者已从 `requirements.txt` 移除，打包也不再
  需要系统 `dot` 二进制。
