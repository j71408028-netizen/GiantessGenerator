# v1.0.0 → 2.0.0-alpha 版本过渡点分析

> 面向维护者：本文回答「从 v1.0.0 到当前 `2.0.0 alpha` 之间，应该在哪几个提交切版本」。
> 全部数字来自 git 实测（2026-10-09）。

---

## 0. 两点必须先说清的前提

### 0.1 `v1.0.0` 不是 `HEAD` 的祖先

`release/v1.0.0` 自 `befca6f`（2026-09-01「20260901功能新增」）分出，只额外加了
一个定稿提交 `9785356`（改 `APP_VERSION` + `Events.json` 换新版）。而 `main` 自
`befca6f` 继续向前，两者**平行分叉**。

所以「v1.0.0 至当前」有两种口径：

| 口径 | 区间 | 结果 |
|---|---|---|
| 严格按 tag | `v1.0.0..HEAD` | 266 文件、+55407 / −8289 |
| 按共同祖先（推荐） | `befca6f..HEAD` | 265 文件、+55256 / −8043 |

差异只有 2 个文件（`paths.py` 版本号 + `Events.json` 描述风格），**不影响结论**。
本文其余统计一律用 `befca6f` 作基准。提交数：**76**（首父路径 75 + 1 个 merge）。

### 0.2 版本号轨迹（实测，来自 `paths.py:APP_VERSION`）

| 提交 | 日期 | `APP_VERSION` |
|---|---|---|
| `befca6f` | 2026-09-01 | `1.0.0 preview` |
| `93ad455` / `a82f5de` / `2df37e2` | 09-08 → 09-28 | `1.0.0 preview`（未动版本号）|
| **`a35fc89`** | **2026-10-05** | **`2.0.0 alpha`** ← 首个改号提交 |
| `93de7ae` … `HEAD` | 10-06 → 10-09 | `2.0.0 alpha` |

**关键事实**：作者把 `1.x → 2.x` 的切换点定在 **2026-10-05**——即「副本音效 + 小游戏 +
角色聊天」三个功能落地之后、**目录分层重构之前**。也就是「功能齐了先升号，重构与跨平台
留作 2.0.0 的收口」。这条既有标记是后文方案的锚点。

## 2. 推荐的版本过渡点

### 2.1 主方案（推荐）

以**功能世代**切 1.x，以**结构性不兼容**切 2.0：

| 版本 | 边界提交 | 日期 | 主题 |
|---|---|---|---|
| `v1.0.0` | `befca6f` | 2026-09-01 | 已发布基线（扁平布局） |
| **`v1.1.0`** | `1e46346` | 2026-09-13 | 地址系统 + 演化/档案重写（E1） |
| **`v1.2.0`** | `2df37e2` | 2026-09-26 | 副本世代重构 + 主题配色（E2） |
| **`v1.3.0`** | `e3dc12f` | 2026-09-28 | ME模式 / 挂件界面（E3） |
| **`v1.4.0`** | `bc15728` | 2026-10-05 | 音效 + 小游戏 + 聊天（E4） |
| **`v2.0.0-alpha.1`** | `3c7db94` | 2026-10-06 | 目录分层重构收口（E5） |
| **`v2.0.0-alpha.2`** | `2c67a95` | 2026-10-07 | Linux 支持 + 工程化收口（E6） |
| **`v2.0.0-alpha.3`** | `HEAD` | 2026-10-09 | 开发者工具 + 界面打磨（E7）← **当前** |

**为什么 2.0.0 从 E5（目录分层）起算而不是从 E4（改号点）起算**

`a35fc89`（10-05）把版本号改成 `2.0.0 alpha` 是**提前打标**：当时功能已齐、重构未做。
但从"版本号应对应不可逆的能力变化"这个角度，真正配得上 major 的是 E5：

- **对源码分发的 Python 应用，模块布局本身就是公开 API**。E5 之后根目录只剩
  `paths.py` + `main.py`，包路径整体重排（`logic.py` → `core/logic/`、
  `context.py` → `services/exploration/`、`services/xxx_service.py` → 子域包……）。
  世界包行为包作者按文档写的 `from services.creation_service import …` 是少数被
  刻意保留的契约（`docs/architecture.md` §2.5），其余路径全部变了。
- E6 的跨平台（Linux/X11 从"不支持"到"受支持"）是**平台面上的能力扩张**，不是补丁。

二者叠加，构成 2.0.0 的实质内容。E4 之前的 1.1–1.4 全部是**纯增量功能**，在
`1.0.0 preview` 这个号下一路开发，适合作为 1.x 线的四个过渡点回填。

### 2.2 备选方案（尊重既有标记）

若坚持"`APP_VERSION` 一改就必须算 2.0.0"的严格口径：

- `2.0.0-alpha` 起点改为 **`a35fc89`（2026-10-05）**；
- 则 E4 归入 2.0.0-alpha 的功能收集期，1.x 线只到 `v1.3.0`（E3）；
- E5/E6/E7 依次作为 `alpha.1` / `alpha.2` / `alpha.3`。

即：**1.1 / 1.2 / 1.3 三个过渡点 + 2.0.0-alpha.1~.3**。

两套方案的**提交边界完全相同**，只是「10-05 那一刀」算 1.4 还是 2.0.0-alpha 的差别。

（这些过渡点当时一个都没有落标，原因不在代码侧，见下节。）

## 3. 期间未发布的原因：资源创作跟不上

上述 1.1 ~ 1.4 四个功能世代始终停在 `1.0.0 preview` 号下、最终被并进 2.0.0，
**不是因为没有可发的代码，而是因为配套的资源创作没跟上**。

本仓的"版本"不只是代码快照：一份可发布的版本 = 代码能力 **+** 该能力依赖的内容资源
（地标 / 描述 / 副本方案 / 静态表 / 地址）。这一期间代码侧每一代都推进得很远，资源侧
却基本停在 v1.0.0 的规模，于是这些世代缺乏"可交付的内容面"，只能先不落标。

实测的资源缺口（2026-10-09）：

| 对应世代 | 代码能力 | 配套资源现状 | 缺口 |
|---|---|---|---|
| E1 地址系统 | 地址申领 / 注册表 / 跨世界引用（`docs/address_system.md`） | `data/packs/landmarks/ChineseMix.addr.json` 仅 **1 条**已申领地址（`2e6_3e5_5e4@RW-CN1`） | 机制完整，但可供引用的地址几乎为空 |
| E2 副本世代重构 | 章节 / 触发器 / 结局 / 素材导入（编辑器全套） | `data/packs/scenarios/` 只有 `_default` 一个方案 | 缺配套剧本 |
| E2 / E4 组件与音效 | `component_pack`、语音 / 音效 / 章节配乐 | `data/packs/quips/` 仅 2 个风格（`Events` / `PixelGame`） | 缺对应语料与素材 |
| 各代 | 静态表机制 | `data/static/{names,personalities,presets,news}` 各 1 份 `default.csv` | 表内容单薄 |

**建议：资源写好一代就补发一代**，尤其优先补齐与新增代码功能直接对应的部分——
首推**地址**，其次**副本方案**，再次**描述与静态表**：

1. **地址优先（对应 E1）**：它是本期间唯一"机制建好了却几乎没有内容"的功能，缺口最醒目；
   补上后 `v1.1.0` 才有独立发布的价值。
2. **副本方案次之（对应 E2 / E4）**：编辑器与运行时都已完备，缺的只是剧本；
   剧本到位即可支撑 `v1.2.0` / `v1.4.0`。
3. **描述与静态表（对应各代 UI / 组件）**：属持续增补，可随任意一代补发。

**为何要"适时补发"而不是攒齐再发**：各代的代码能力已经冻结在不可变提交里，补发只受
资源进度约束——资源到位一代就发一代，可避免"代码走了三代、用户侧内容还停在 v1.0.0"
的脱节；若攒齐再发，§2 的全部过渡点会被推到最后一并释放，等于放弃 1.x 线本身。

## 4. 落地建议

1. **边界提交都已有、不可变**，回填标签成本极低——直接打**附注标签**即可，
   注记按 `docs/Releases/release.md` §1 的格式写「包含什么、从哪个提交分出」。
2. **版本号与标签必须一致**（`release.md` §2）：若回填 `v1.1.0`~`v1.4.0`，
   需要在这些边界提交上各起一次 `APP_VERSION` 的改号提交，或接受这些标签
   是"考古标签"、`APP_VERSION` 不对齐（**不推荐**，会破坏 `release.md` 的单一口径）。
3. **`2.0.0 alpha` 带后缀是允许的**（`release.md` §2 明确 `APP_VERSION` 允许带后缀），
   但**正式发布点必须用纯 `<X.Y.Z>`**——所以 `v2.0.0` 定稿前要把
   `APP_VERSION` 从 `2.0.0 alpha` 收敛为 `2.0.0`，并归零三种 alpha 子阶段。
4. **推荐最小动作**：只补 **`v1.4.0`（`bc15728`）** 与 **`v2.0.0-alpha.1`（`3c7db94`）**
   两个标签——前者是 1.x 线的功能收官、后者是 2.0 结构性分界的起点，
   信息量最大；其余过渡点留在本文档中备查，不必全部落标。
