# 副本内的地点与参照物

> **这一篇回答什么问题**：副本里"这是哪儿"要不要用地址？地址用在哪三处、怎么用？
> 尺寸换算句的参照物从哪来？读者：改副本提示词 / 结算 / 编辑器的人，以及写方案的
> 作者。

相关：[报告生成](report_selection.md)（主世界怎么用位置与地标）、
[地址匹配](address-system/matching.md)（`relate` 的空间关系与私有名）、
[数据模型](../Dungeon/script.md)（章节与方案的字段索引）。

## §1 地址是声明，不是推断

副本里没有移动、没有寻路，也没有"从 A 走到 B"的移动叙述：这一章发生在哪儿，是
作者写死的。所以地址在副本里不承担**求解**职责，只承担**声明**职责。

三条用途都建立在"作者把地点写死"之上（前两条读章节 `address`，第三条读结束章节的
`exit_address`）：

| 用途 | 读什么 | 不声明时 |
|---|---|---|
| 展示 | 章节 `place` / `address` → 提示词一行（§7） | 什么都不显示 |
| 参照物 | 用地址过滤全局地标池（§4） | 用方案自带清单；都没有就是全局全量 |
| 传送 | 结束章节 `exit_address` 写回角色 `position`（§8） | 位置不变 |

一条硬推论：**没写章节地址的旧方案行为完全不变**（§10 第 1 条）。地址是逐章可选的
增强，不是新的必经环节。

## §2 不要的：自动匹配

曾有一版方案把主世界的坐标匹配整套搬进副本（距离筛选、三级降级、`dgn_*` 维度隔离）。
它解决的是"她此刻在哪、哪些地标够得着"——副本里这两个问题都被作者回答了，再算一遍
只会引入新的失败模式：巨型尺度下"10 倍身高"恒真、章节是图而配置是列表、外部地标
把场景带偏。

现在保留的只有一条判据：**这个地标是不是在这一带**，用地址自身的空间关系判断，
不用米数。

## §3 字段

方案顶层（`dungeon/schema.py`）保留一份自带清单：

```json
"scene_landmarks": [
  {"name": "黑塔", "size": 468, "dimension": "vertical"},
  {"name": "断门", "size": 120, "dimension": "vertical"},
  {"name": "护城河", "size": 40, "dimension": "horizontal", "horizontal_type": "length"},
  {"name": "石阶", "size": 0.4, "dimension": "vertical", "frequency": "common"}
]
```

章节：

```json
{
  "name": "第三章",
  "place": "黑塔脚下的集市",
  "address": "1e3_1e2_1e1@HD!RW-CN1-HD",
  "landmarks": ["黑塔", "护城河"],
  "exit_address": "1e3_1e2_1e1@HD!RW-CN1-HD-9"
}
```

| 字段 | 位置 | 类型 | 默认 | 说明 |
|---|---|---|---|---|
| `name` | 地标 | str | 必填 | 直接进提示词 |
| `size` | 地标 | float | 必填 | 米；`vertical` 为高度，`horizontal` 为长度 / 宽度 |
| `dimension` | 地标 | str | `vertical` | `vertical` / `horizontal`，与 `core.models.Landmark` 同义 |
| `horizontal_type` | 地标 | str | `length` | `horizontal` 时用 |
| `frequency` | 地标 | str | `unique` | `unique`（"约等于 X 高度的 0.63 倍"）/ `common`（"相当于 X 的高度"） |
| `place` | 章节 | str | `""` | 展示名；提示词与窗口都用它 |
| `address` | 章节 | str | `""` | 取景地址（完整地址，见 §4） |
| `landmarks` | 章节 | list | `null` | 本章从自带清单里取哪几个；`null` = 全清单，`[]` = 本章不用清单 |
| `exit_address` | 章节 | str | `""` | 结局传送目的地（§8） |

`scene_landmarks` 缺省 `[]`，章节四字段缺省空——旧方案读进来与改动前等价。
`normalize_chapter` / `normalize_scene_landmarks` 负责把写坏的形状（非数组、非对象、
类型不对）归一回默认值，运行期不因一条坏数据中断。

## §4 候选池：清单 + 地址过滤

```
本章清单（scene_landmarks 按 landmarks 白名单过滤）
  ∪ 地址相配的全局地标（仅当章节写了 address）
```

| 章节 `address` | 方案 `scene_landmarks` | 候选池 |
|---|---|---|
| 无 | 无 | `merged_landmarks` 全量（**= 改动前**） |
| 无 | 有 | 只有清单 |
| 有 | 无 | 只有地址相配的全局地标 |
| 有 | 有 | 并集，同名以清单为准 |

**"地址相配"的定义**：`relate(chapter.address, 地标完整地址).pairable()`——同址 /
包含 / 被包含，且私有名约束互相满足。就是主世界判定"内容在不在这个位置"用的同一个
原语，不另立规则。

不做米数阈值。巨型尺度下任何 `reach`（10 倍身高、格宽几倍）都会恒真，这正是上一版
退化成"有 / 没有"两态的原因；而"是不是同一格、同一区"不随身高变化。

**地址的层级就是取景范围**：写在三级地域 = 只这一格及挂在它下面的地标；写在二级 =
整个区；只写维度 = 整个世界（私有名的限制见下）。作者要城市章节能用全城地标，就把
章节地址写在一级地域。这是一个显式、可读的旋钮，不需要再发明距离参数。

**私有名要对上**：地标若声明了 `@abc!`，章节地址也必须声明同一个私有名（只写 `@*!`
不算——约束要互相满足才算配对）。所以"只写维度"只对没有私有名的地标有效；要覆盖一个
带私有名的世界，章节地址得写成**那个世界的注册地址**。最省事也最不容易错的写法就是
直接抄风格注册地址，再按需加细一级。

**必须写完整地址**（带 `@` 规模段）：章节地址没有"风格注册地址"作基准，相对后缀在这里
解析不了。编辑器给一个"选一个已注册地址 → 填入文本"的选择器即可，抄文本、不建引用
（与 §6 的地标数值同一种做法）。

**没地址的地标不参与相配**：写了地址的章节是在要求精确，放行无主地标等于把精度又
丢掉；声明了 `address_mode="portable"` 的同样跳过——那是作者显式说明"不参与地址规则"。
`frequency`（`unique` / `common`）不参与这个判定，只影响换算句的措辞。真需要"一层楼
那么高"这类通用参照，写进自带清单即可。

**地址写坏 = 没有地址**（只剩清单），校验器报 error。不回落全量——解析不了的地址
说明作者本意是限定范围，回落全量正好是反的。

## §5 选取：仍是两态

```
本章候选池 → get_comparisons(order="match", limit=1)
  ├─ 有候选 → 换算句
  └─ 没有   → 不产生换算句（正文照常推进）
```

- 不返回 tier，也没有任何"能否继续"的判断读它——推进由章节与触发器决定；
- 名字命中全局屏蔽词（`blocked_words`）的条目按现状跳过；
- 体位筛选（`vertical` / `horizontal`）沿用 `get_comparisons` 既有规则；
- 候选池按章节名缓存，切章失效（身高变化不影响池子）；
- **空池就是空池**：作者把范围限死到没有候选时，不产生换算句，也不回退全量。

## §6 全局池怎么进子进程

副本会话在独立子进程里跑，那里**没有地标仓库，也没有风格注册表**：`Landmark.address`
只是相对后缀，子进程解析不出完整地址。所以地址必须在父进程解析好再进载荷：

- 启动前把 `merged_landmarks` 换成"每条带完整地址"的纯数据（`address` = 组合后的
  完整地址，`address_mode="exact"`），走 `dungeon/window/launch_payload.py` 的
  序列化 / 还原；
- 解析复用主世界那套 `AddressPlanner`（`services/exploration/address_plan.py` 的
  `landmarks_for_export()`），不新写一份组合规则；
- 解析失败的地标**照样进载荷**（名字、尺寸不变，只是标成 `portable`，不参与地址相配），
  不能因为一条坏地址让整个地标消失。

顺带说明"运行期不查仓库"不是纪律问题：子进程里根本没有仓库可查。

## §7 展示

- `dungeon/scene.py::place_label(chapter)`：`place` 优先，否则 `format_addr_compact(address)`
  的紧凑描述；两者都空则返回空串。作者起的名字总压过地址原文，写了 `place` 的章节
  不会把带精度说明的地址串漏到界面上。
- 提示词：`build_user_prompt` 在 `当前章节：…` 之后按需追加一行 `当前地点：…`
  （仅在非空时；虚构章节不写地址，这一行就不出现）。
- 会话访问器 `DungeonWindowBase.current_place()` 包的是同一个函数，留给窗口组件用；
  目前只有提示词在读地点，窗口侧尚无组件消费它。

**把地址写进提示词是有意的**：写实副本要的就是"她在一座真城市里"，模型知道地名
才会写出相称的街景；虚构副本根本不写地址，也就没有东西可漏。

## §8 结局传送

`exit_address` 决定"她出来后站在哪"，是副本改写主世界位置**唯一**的入口。

| 情形 | 行为 |
|---|---|
| 结束章节 | `DungeonStoryEngine._terminate_from_ending_chapter` 组装结算字段时带上 `chapter.exit_address` |
| 结算 | `scene.landing_position()` 能 `parse_full` 才算数：`char.position = exit_address`，并让那条演化行带 `position`（空间档案据此学到访） |
| 本局尚未创建角色 | 暂存到 `_pending_exit_position`，`_create_character_from_session` 建角色时作为初始 `position` 写入，用后清空 |
| 字段为空 / 解析失败 | 位置不变（**默认**，绝大多数结局） |

传送只有"结束章节"这一个入口：旧版 `ending` 触发器动作已退场（运行时跳过，见
`docs/Dungeon/script.md` §3.2），所以 `action_data` 里没有 `exit_address` 这条路径，
校验器也只检查章节字段。

允许跨维度：传送本来就是跨空间的事，不加"必须与入口同址"的限制。

进门仍是"门是门"，不改位置：角色有地址时只按入口地址（`entry_address`）算距离做
准入判定，判定通过后位置不动。

## §9 校验（`dungeon/validate.py`）

| 问题 | 级别 |
|---|---|
| `size` 非数 / ≤ 0 | error |
| `dimension` 非法 | error |
| 清单内重名 | error |
| 章节 `landmarks` 引用了清单里不存在的名字 | error |
| 章节 `address` / `exit_address` 无法解析 | error |
| 名字含换行或超过 40 字（直进提示词） | error |
| `scene_landmarks` 不是数组 | warning（按空清单处理） |
| `frequency` / `horizontal_type` 取值非法 | warning（回落默认） |
| 章节 `address` 与入口地址跨维度 / 跨一级地域 | warning（只提示，不拦截） |
| 清单里只有一种 `dimension` | warning |
| 章节 `landmarks` 为空列表 | 无提示（是设计） |

编辑器在存盘前用同一套地址解析拦一遍坏地址（`ui/scenario/chapter_dlg.py`），道理是
运行期遇到坏地址只会静默当没写，不如当场说清。

## §10 验收（`tests/check_dungeon_scene.py`）

1. **四种组合**：无地址无清单 → `merged_landmarks` 全量，提示词与改动前逐字一致；
2. **地址过滤的粒度**：同址 / 祖先 / 子孙进池，兄弟格与另一维度不进；私有名必须
   互相满足；
3. **白名单三态**：`null` = 整份清单，`[]` = 本章不用清单（**不回落到全量**），
   列表 = 只取被点名的，陌生名字被忽略；
4. **坏地址**：只留清单、不回落全量；无清单则池子为空；校验 error；
5. **影响不到推进**：改清单 / 改地址不改变可达章节与结局集合；
6. **会话访问器与提示词**：`chapter_landmarks()` 按章节缓存、切章失效；换算句取自
   本章池子；空池不产生换算句；
7. **载荷里的完整地址**：父进程解析 → JSON 往返 → 子进程仍能地址相配；
8. **展示**：`place` / 紧凑地址 / 空三种形态，地点行紧跟章节行，虚构章节不出现；
9. **结局传送**：写回 `position` 并留带 `position` 的演化行；坏地址不动；未建角色
   时暂存且只消费一次。

第 1 条是这轮改动的核心承诺；第 5 条说明"候选池随玩家世界而变"是可接受的——它只
影响措辞，不影响这局会走到哪里。
